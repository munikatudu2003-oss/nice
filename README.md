# wechat-article-agent

一个用于“读取配置表 → 抓取微信公众号文章 → 产出结构化结果”的自动化实验仓库。

> 当前仓库仍处于早期阶段：README 以“已实现的最小可运行流程 + 明确的现实限制”为准，不把未落地模块写成已完成。

## 项目目标（当前真实状态）

- 建立可迭代的文章处理工作流雏形。
- 先打通 **mock 输入到 mock 输出** 的端到端流程，确保流程可验证。
- 在流程稳定后，再逐步接入真实 Feishu 读表、真实抓取与更完善的模块拆分。

## 当前可用流程（Mock）

1. 准备一份本地 mock 输入（模拟配置/任务列表）。
2. 执行当前脚本，按顺序处理每个 mock 任务。
3. 生成输出文件（见下文“输出文件”）。
4. 人工检查结果内容与字段完整性。

> 该流程用于验证“流程和数据形态”是否正确，不代表生产级抓取能力已完成。

## Python 解释器说明（重要）

目前系统默认 `python` 仍不稳定，因此请优先使用临时可用解释器执行命令。

示例（请按你机器上的实际路径替换）：

```bash
/tmp/python312/bin/python --version
/tmp/python312/bin/python your_script.py
```

如果你已经在本机创建并验证了其他稳定解释器，也可以替换为你的可用路径。

## 输出文件

当前流程会产出用于调试/验证的结果文件，通常包括：

- 原始输入快照（便于复现）
- 处理后的结构化结果（JSON/CSV 等）
- 运行日志（排错用）

建议将输出统一放在 `output/`（或你当前脚本约定的目录）下，便于后续接入真实入口时保持一致。

## 已知风险与限制

- **唯一保留的现实限制**：默认 `python` 不稳定，需显式使用临时可用解释器。
- 当前以 mock 流程为主，真实外部依赖（如 Feishu API、公众号抓取稳定性）尚未全部接入。
- 目录结构仍偏轻量，后续重构时会调整模块边界。

## 下一步建议

你可以按优先级二选一推进：

1. **先重构项目结构**：扩成 `agents/ services/ utils/ config/`，把职责边界先固定。  
2. **先接真实入口**：优先打通 Feishu 读表入口，再逐步替换 mock 数据源。

推荐顺序：先确定你更在意“工程结构稳定”还是“业务链路先跑通”，再选其一做第一步。
